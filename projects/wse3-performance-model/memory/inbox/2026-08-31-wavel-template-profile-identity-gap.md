# Wavel template/model identity gap — 2026-08-31

**Project:** wse3-performance-model  
**Author:** codex  
**Status:** captured

## Verified finding

- Wavel's CSL materializer dispatches compute events to concrete `Kernel` generators, including distinct Cannon and SUMMA bodies for the same `matmul`/`gemm` operation type. The selected body depends on an explicit algorithm attribute or the program rectangle.
- The current mapping cost path dispatches by `op_type`; its GEMM call does not carry the code generator's selected algorithm and the predictor defaults generic `gemm` to `meshgemm`. Consequently, a `matmul` priced with one implementation model can be materialized by another body—for example, a SUMMA-priced instance could be emitted as Cannon if their template identities are not preserved.
- Wavel also has six concrete `CollectiveTemplate` identities and one bounded east-only `MOVE_KERNEL`; predictor aliases and IR operation names cover a broader set and are not proof of CSL materializability.
- Le confirmed the governing decision: performance models are defined directly over backend-qualified, versioned implementation-template instances, and the same template identity must survive modeling, query/result handling, CandidatePlan selection, and materialization. Two templates may implement the same logical operation yet require different model and cache identities; `op_type`, shape, or a loose source reference alone is insufficient. Template granularity may be atomic, fused, or role-level, but any hierarchy/composition must remain explicit and must not double-count a fused model with its children.
- Le confirmed the resource-authority split: a template catalog or claim resolver may return versioned template-local code/state/scratch/buffer/protocol claims (`known`, `upper_bound`, or `unknown`), and Wavel may use them only for conservative necessary-condition pruning. Neither M2 nor Wavel may return target-wide `feasible=true`; KAIR closure remains authoritative for resource sufficiency, coexistence, exact colors/queues/tasks/routes/buffers/lifetimes, and final legality.
- Le chose the public identity vocabulary `TargetHardware`, `TargetEnvironment`, and `ImplementationTemplate`. Generator selection/body metadata is embedded in `ImplementationTemplate` rather than exposed as a peer `CodegenEntry` identity: selecting the template already fixes the generator, while candidate-specific bound parameters remain a separate implementation-variant identity. `TargetEnvironment` describes the SDK/ABI and closure-schema environment; operator placement/PE geometry belongs to the candidate or implementation variant, not the target topology.
- Le confirmed the public model vocabulary and cardinality: an `ImplementationTemplate` has many bound `ImplementationVariant`s; immutable `ImplementationWitness` result groups observe exact variants; a `ModelCalibration` selects multiple compatible witnesses and reproducibly produces one model artifact; and a `PerformanceModel` is the versioned prediction function with embedded applicability and metric boundary. A performance query selects one exact variant and one compatible model, not an individual witness. Bound template parameters are model inputs. The first contract does not add a generic concurrency dimension: a stable collocated/co-executing implementation becomes a new fused template/variant and is profiled directly. Separate models are required only when target environment, metric boundary, model artifact/evidence set, applicability, or version differs—not merely because one bound input parameter has different values.
- Le selected a deliberately simple runtime mapping: once Wavel has fixed an exact `ImplementationVariant`, `PerformanceQuery` names the exact active canonical `PerformanceModel` and provider directly. Model/provider selection is not a Wavel planning knob and does not require a two-stage runtime resolution object. Historical model/provider versions may remain for reproducibility, but the active registry mapping for one template revision, target environment, and metric is unique.
- Le confirmed that S2 must retain explicit extrapolation semantics rather than imposing a contract-wide rejection rule. A model must distinguish calibration-domain use, bounded extrapolation, and out-of-domain failure; the exact bounded-domain and uncertainty/ranking policy remains to be settled rather than silently inferred.
- Le chose a deliberately bounded first storage/offload abstraction: model the fixed blocking KV-offload pattern as a normal Wavel peer/coarse kernel template using the same variant→witness→calibration→model chain, with `event_driven_role` only as an `ImplementationTemplate` mode. The workload/CandidatePlan fixes a trigger such as one transaction after X decode invocations; the model predicts one transaction and assumes no arrival distribution or generic service queue. Outbound/return legs use ordinary movement semantics, while any persistent SRAM object is a separate resource-lifetime fact. Stable collocated/co-executing kernels should initially become a new fused template rather than a generic concurrency model. This direction preserves the audited v3/v4/v5 verify-not-store limitation and does not claim actual KV residency.
- Le accepted a minimal first public surface: target hardware/environment, implementation template/variant/witness, model calibration/model, one canonical registry entry, direct performance query/prediction, and one local resource-claim set. Helper abstractions for query envelopes, runtime registry resolution, storage-specific profile/admission, aggregate resource envelopes, public cache identities, and composition specs are not first-contract public classes.
- Le selected a three-state provider result: `supported`, `unsupported`, or `unknown`. Invalid or internally inconsistent queries fail through an SDK `QueryValidationError` before provider invocation, produce no `PerformancePredicted`, and do not enter the prediction cache. `out_of_domain` is an `unsupported` reason unless the point is inside an explicitly declared bounded-extrapolation domain; `needs_compile` is not a first-contract status.
- Le selected structured nested reason records rather than a bare enum list or hierarchical string code. Each reason has a required stable flat `code` plus optional typed `subject_path`, `boundary_ref`, and `evidence_ref`; an optional human `message` is non-semantic, and arbitrary `details` maps are disallowed. The compact first-contract taxonomy is channel/status-specific: validation uses `MISSING_REQUIRED_FIELD`, `UNSUPPORTED_SCHEMA_VERSION`, `INVALID_CANONICAL_ENCODING`, `QUERY_DIGEST_MISMATCH`, `UNRESOLVED_REFERENCE`, `INCONSISTENT_IDENTITY`, and `INVALID_VALUE_OR_UNIT`; unsupported results use `UNSUPPORTED_TEMPLATE`, `UNSUPPORTED_TARGET_ENVIRONMENT`, `UNSUPPORTED_METRIC`, `OUT_OF_MODEL_DOMAIN`, `EXTRAPOLATION_NOT_SUPPORTED`, `NO_BOUNDED_MATERIALIZATION`, and `UNSUPPORTED_PROTOCOL_MODE`; unknown results use `MISSING_MODEL_ARTIFACT`, `MISSING_CALIBRATION_EVIDENCE`, `MISSING_RESOURCE_CLAIM`, and `INSUFFICIENT_INTERFERENCE_EVIDENCE`.
- Le selected template-declared required resource claims. Required means that a claim kind must be present and audited, not that its value is known or positive. A `ResourceClaimSet` is `supported` only when every required claim is known or upper-bounded with provenance, `unknown` when any required claim is explicitly unknown, and `unsupported` only when the exact variant cannot be expressed by the declared claim schema or has a template-local contradiction. These states never answer target-wide sufficiency, which remains KAIR authority.
- Le selected a neutral first-contract SDK package in `wse3-performance-model`: shared types, canonical serialization, validation, reason enums, and identity rules must not depend on Wavel internals, provider implementations, or KAIR internals. M2 provider/resolver code and future M3 Wavel integration import this package.
- Le selected a minimal nested `event_interface` for `event_driven_role` templates: trigger input schema, completion output schema, bounded invocation boundary, serial reentrancy, persistent-state schema reference, and deployment-claim schema reference. Trigger frequency remains workload/CandidatePlan configuration rather than a performance-model input.
- Le confirmed that the embedded generator source identity is named `generator.source_ref`, not `implementation_revision`, and remains a nested `ImplementationTemplate` field rather than a peer public class. U2 has three mechanism templates (v3 single-row, v4 GO-chain, and v5 cascade), each with distinct `owner_receive_mode: control_task | bulk_fabin_dsd` materialization-relevant variants. Legacy `task`/`dsd` spellings remain source provenance because the audited implementation verifies synthetic return data rather than storing and reloading real KV.
- Le corrected the evidence-production dependency: M1-S3 freezes canonical implementation/config baselines and benchmark requirements—exact variants, template coverage, metric/timing boundary, correctness oracle, parameter matrix, repetitions, uncertainty requirements, and required resource claims—but creates no real witness or model. M2 owns identical-variant materialization/conformance, new U1/U2 experiments, immutable raw results and correctness records, `ImplementationWitness`, `ModelCalibration`, `PerformanceModel`, provider/resource resolver implementation, and registry population. M3 may import baseline identities in parallel but must wait for registered M2 results before reproduction, costing, or search validation. Legacy U2 measurements/fits remain planning and regression inputs; the first provider profiles are generated anew under the S2 contract. Consequently S2 requires fixture plus S3 baseline/benchmark-manifest round-trips, while real witness/model round-trips are M2 acceptance gates.

## Implications / next actions

- [ ] Audit the use-case-required atomic and fused templates before deciding which profiles to populate.
- [ ] Map the existing Qwen decode/prefill role pipeline and the v3/v4/v5 storage-offload implementations onto the template catalog, marking exact, partial, and missing coverage; use the gaps to define template-completion work and the covered set to select required performance tests.
- [ ] Require query/result/cache identity to change when the selected template body, selection-relevant attributes, backend, target environment, performance model, SDK, or template composition changes.
- [ ] Preserve the transitive witness set through `ModelCalibration` and `PerformanceModel` provenance without adding witness selection to each performance query.
- [ ] Keep predictor-only support distinct from materializer support; fail closed when no matching bounded template exists.
- [ ] Use direct `claims(ImplementationVariantRef) -> ResourceClaimSet` rather than a feasibility/admission provider, and preserve every unknown through the Wavel-to-KAIR handoff.
